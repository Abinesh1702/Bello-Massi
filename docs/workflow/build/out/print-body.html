01 · Application Overview

1.1 What Bellomassi is

Bellomassi is an order-to-delivery management system for a frozen and chilled food distributor. It covers the full chain from a salesman (or the customer) placing an order, through sales approval, warehouse preparation, dispatch planning and the driver’s doorstep delivery, to the delivery note and the customer invoice. Around this core it provides inventory control, vehicle and driver compliance, document management with OCR, communication (email, WhatsApp, call log), reporting, forecasting and an AI assistant.

The application in this repository is a client-demo prototype:

  • It is a single React web application. There is no backend server and no database.
  • All data lives in the browser’s LocalStorage (application data version 8). Each browser has its own copy of the data; clearing site data resets it to the seeded demo data.
  • Sign-in is a browser-session simulation with published demo passwords. It is not production authentication.
  • Integrations (SMTP email, OpenWA WhatsApp, OCR, AI providers) have a demo mode that is active by default and an optional backend gateway mode that is only used when VITE_INTEGRATION_GATEWAY_URL is configured. Gateway mode is Not Verified in this document because no gateway was available.

02 · Overall Workflow

2.1 The business in one paragraph

A Sales Executive (or the customer in the customer app) raises an order for a customer and a fulfilment hub. The Sales Manager checks credit, stock and data quality and approves, returns or rejects it. Customer Service verifies the approved order against the warehouse and consolidates it, then marks it ready for dispatch. The Dispatcher groups ready orders into a dispatch, assigns a compliant driver and vehicle, and confirms the dispatch — at that moment hub stock is deducted and a delivery record is created for each order. The Driver starts each stop in sequence, records arrival, collects the customer’s OTP, captures quantities and proof of delivery, and completes or fails the stop. Completing a stop generates a delivery note. Finance issues the invoice from the order (on ordered or delivered quantities). Failed and partial deliveries go back to the Dispatcher for review. Around this flow, the warehouse roles keep stock accurate (receipts, transfers, adjustments, scrap), the QA Manager verifies documents and watches expiry, and every step raises in-app notifications and optional email / WhatsApp messages.

2.6 Key rules that hold across the whole flow

  • One step at a time. Each service refuses an action when the record is not in the expected status (for example, a dispatch can only be confirmed when it is ASSIGNED; a delivery can only be completed when it is OUT_FOR_DELIVERY).
  • Permissions are checked twice — the route (ProtectedRoute + navigation.js permission) and the service (can(user, key)), so a hidden button cannot be bypassed.
  • Stock moves exactly once. Dispatch confirmation deducts stock once (stockDeducted flag); cancellation reverses it once (stockReversed); a reviewed exception returns stock once (returnedToHub); a scrap request writes off once.
  • Everything is traceable. Orders have a timeline (bellomassi_order_timeline), dispatches have a timeline (bellomassi_dispatch_timeline), administrative changes go to the audit log (bellomassi_audit_logs) and user activity to bellomassi_activities.
  • Nothing is deleted after submission. Only draft orders can be deleted; submitted orders are kept for the audit trail.

  1. The user chooses Sign Out (header menu, sidebar, driver profile or customer profile) → /logout confirmation.

3.7 Route protection

  • src/routes/ProtectedRoute.jsx sends signed-out visitors to the right sign-in page and checks the page’s permission from navigation.js. A signed-in user without the permission sees /unauthorized.

Status: Implemented end to end. GPS tracking and the delivery OTP are Simulated (no GPS device, no SMS).

6.1 Business summary

  1. An order is raised by a Sales Executive (/orders/create) or by the customer (/customer/cart).

  3. Customer Service consolidates it after a five-point verification and marks it ready for dispatch.

8.1 The driver’s day in plain English

  1. Sign in on the phone at /driver/login (mobile number, email or username).
  2. Today shows today’s and tomorrow’s stops “published by the Dispatcher”, the next stop, an ETA plan and personal performance for the selected period (default Today).
  3. Nothing can start until the Dispatcher confirms the dispatch (vehicle loaded, stock deducted).
  4. Open the first stop → Start delivery. The order becomes Out for delivery, a DEMO GPS session starts and the customer and Dispatcher are notified.

  8. If the delivery cannot happen → Report issue / mark failed with a reason. The Dispatcher reviews it.
  9. Move to the next stop. When every stop is closed, the dispatch closes as Completed or Closed with exceptions.
  10. Sign out from Driver Profile.

11 · Dispatch & VMS Workflow

Status: Dispatch planning, assignment, confirmation, cancellation, sequencing, delivery review and VMS compliance are Implemented. Live tracking is Simulated (DEMO GPS). Route optimisation is a suggested sequence, not a road routing engine.

11.1 Business summary

The Dispatcher works from the Ready for Dispatch queue. A dispatch is one vehicle run from one hub on one date. It holds a set of orders in a delivery sequence, one driver and one vehicle. Before anything leaves the hub, the system checks that every order is still ready, that the driver and vehicle are free, from the same hub, legally compliant and that the load fits the vehicle. Confirming the dispatch is the loading sign-off: hub stock is deducted and the driver can start. The Dispatcher then follows the run on Delivery Tracking / Live Tracking and resolves failed and partial stops.

Finance (or an Administrator) picks an approved-or-later order and issues one invoice for it. The invoice is a frozen snapshot of the order, customer, hub, template and — when available — the delivery note, so later changes to master data never change an issued invoice. Finance chooses whether to bill ordered quantities or delivered quantities (from the delivery note), can add an order discount, shipping and additional charges, and sets invoice and due dates. An invoice that is wrong is cancelled with a reason; a new one can then be issued.

12.4 Calculation (services/invoiceCalculationService.js)

Line Formula
Line subtotal quantity × unit price
Item discount line subtotal × item discount %
Order discount NONE, flat AMOUNT or PERCENT of (Σ subtotal − Σ item discount), allocated to lines by value
Taxable amount line subtotal − item discount − allocated order discount
Tax taxable × tax % (product rate from the order, or a flat demo rate ≤ 40%)
Charges shipping + additional charges, taxed at charges tax % (default 0, ≤ 40%)
Grand total Σ taxable + Σ tax + charges + charges tax

Quantity basis: DELIVERED bills what the delivery note recorded as delivered; it falls back to ORDERED when there is no delivery note (utils/invoiceSnapshot.js).

15 · Exception Workflow

An exception is anything that stops the normal path. In Bellomassi every exception is handled by the service that owns the record: the action is refused with a message and nothing is saved, or the record moves to an exception status that a named role must resolve. Repeating an action that already happened never changes data twice (“No change was made.”).
